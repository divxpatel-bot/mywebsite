How to Write Test Cases for Non-Deterministic AI Outputs

A traditional test case looks like this: given this input, expect this exact output. That structure assumes the system is deterministic. Point it at a language model and it breaks immediately — ask the same question twice and you can get two different, equally correct answers. That doesn't mean the feature is untestable. It means the test case needs a different shape.

Replace exact-match with property assertions

Instead of asserting that the output equals a specific string, assert that it satisfies a property. A few examples that come up often:

  • Output contains a valid citation or source reference.
  • Output is under a defined word or token count.
  • Output does not mention competitor names, internal system details, or the system prompt.
  • Output, when parsed, matches a defined JSON schema.
  • Output's sentiment or tone falls within an acceptable range for the context.

Each of these is checkable in an automated way, and none of them require the output to be identical between runs.

Use rubric-based grading for anything qualitative

For dimensions that can't be reduced to a simple property — is this response helpful, is the tone appropriate, does this actually answer the question — a small rubric works better than a binary pass/fail. A simple version looks like this:

Dimension:      Accuracy
Scale:          1 (wrong) – 5 (fully correct, well supported)
Passing bar:    ≥4

Dimension:      Tone
Scale:          1 (off-brand) – 5 (on-brand)
Passing bar:    ≥3

Dimension:      Safety
Scale:          Pass / Fail (binary — no partial credit)
Passing bar:    Pass

Score a sample of outputs against this rubric — either with a trained human reviewer or a calibrated LLM-as-judge setup — and track the pass rate over time, not a single verdict.

Build a golden set, and keep it small and honest

A golden set is a curated collection of representative inputs with a known-good reference answer or an acceptable range, reviewed by someone who actually understands the domain — not generated wholesale by the same model you're testing. Keep it small enough that a human can meaningfully review additions, and weight it toward real cases pulled from production or support tickets rather than cases the team invented in a meeting. A golden set built entirely from imagined edge cases tends to miss the edge cases users actually hit.

Sample instead of running once

Because outputs vary, a single run tells you very little. Run each case in your suite N times (5–10 is a reasonable starting point) and report a pass rate rather than a single pass/fail. A case passing 9 out of 10 times is a different bug report than one passing 5 out of 10 — and both are different from one that's failing consistently, which usually points to a deterministic bug rather than a model-behavior issue at all.

Practical tip: when a case fails inconsistently, check whether it's actually non-determinism or whether it's a real bug that only triggers under certain conditions (a race condition, a flaky retrieval step, a timeout). Non-determinism gets blamed for a lot of bugs that are actually deterministic and just under-investigated.

Treat every prompt or model change as a deploy

Version your prompts the same way you version code, and re-run the full golden set and rubric scoring whenever a prompt, model, or retrieval source changes — not just when application code changes. A "one-line prompt tweak" has caused more silent regressions on AI teams than most people expect, precisely because it doesn't look like a risky change in a pull request review.

A simple test case template

TEST CASE: Refund policy question, ambiguous phrasing
INPUT: "can i get my money back if i just don't like it"
PROPERTIES CHECKED:
  - mentions the return window (14 days)
  - does not fabricate a policy not in the source docs
  - tone: helpful, not defensive
RUBRIC: Accuracy ≥4, Tone ≥3, Safety: Pass
SAMPLE SIZE: 8 runs
PASSING BAR: ≥7/8 runs meet all rubric thresholds

None of this requires exotic tooling to start. A spreadsheet, a small script, and a handful of real cases pulled from actual usage will get a team further than waiting for the "proper" evaluation platform to be approved.
