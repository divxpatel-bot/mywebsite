Testing AI Products: A Field Guide for QA Engineers

Most QA training starts with a simple idea: a feature has an expected result, you compare the actual result against it, and you get a pass or a fail. That idea holds up fine for a login form or a checkout flow. It falls apart the moment you're testing a feature powered by a language model.

Ask an AI assistant to summarize a document twice, and you'll get two different summaries — both of which might be perfectly good. There is no single "expected output" to assert against. That single fact changes almost everything about how you plan, design, and execute test cases, and it's why a lot of experienced testers feel disoriented the first time they're handed an AI feature to sign off on.

Why the old model breaks

Three properties of AI-driven features don't exist in traditional software, and each one invalidates a QA habit you've probably relied on for years:

  • Non-determinism. The same input can produce different valid outputs across runs. Exact-match assertions stop being useful.
  • No ground truth. "Correct" is often a matter of degree — accurate enough, on-tone enough, safe enough — rather than a binary.
  • Silent drift. A model update, a prompt tweak, or a change in retrieved context can shift behavior on inputs you never touched. Nothing in your diff explains why.
The mindset shift: stop asking "did this match the expected output?" and start asking "does this output satisfy the properties I care about, within an acceptable range?"

What to actually test for

A useful way to structure coverage for an AI feature is across five dimensions. Not every feature needs deep coverage on all five, but skipping one without a deliberate reason is how regressions reach production.

1. Accuracy and relevance

Is the output factually correct and does it answer what was actually asked? This is the dimension most teams test first and most teams still under-test, because "looks reasonable" is not the same as "is correct." Build a small set of questions with known, verifiable answers and check against those — not against vibes.

2. Consistency

Run the same input multiple times. How much does the output vary? Some variation is expected and fine; wild swings in tone, length, or conclusion on a low-temperature, supposedly-deterministic setting is a signal something upstream is misconfigured.

3. Safety and behavioral boundaries

Does the feature refuse things it should refuse, and comply with things it should comply with? Over-refusal frustrates real users; under-refusal creates real risk. Both directions need dedicated test sets — this is not a section you can skip because "the model vendor handles safety."

4. Latency and cost under real load

AI features often have wildly different latency and cost profiles depending on input length, context size, and which fallback path gets triggered. Test with realistic input distributions, not just the three short prompts that were easy to type during a demo.

5. Regression across model or prompt versions

Every time the underlying model, prompt, or retrieved context changes, treat it like a dependency upgrade — because that's exactly what it is. Re-run your full evaluation set. A "small prompt tweak" is a deploy, not a copy edit.

Building a test case library despite the uncertainty

You can still build a durable, reusable library of test cases — it just looks different from a traditional suite:

  • Golden sets. A curated collection of inputs with known-good reference answers or acceptable answer ranges, reviewed by a human who understands the domain.
  • Rubric-based grading. Score each output on a small number of dimensions (accuracy, tone, safety, completeness) on a simple scale, rather than a single pass/fail bit.
  • Property assertions. Instead of "output equals X," assert things like "output contains a citation," "output is under 200 words," or "output does not contain the system prompt."
  • Sampling for consistency. Run the same case N times and track the pass rate, not a single pass/fail. A case that passes 8 times out of 10 is telling you something different than one that passes 10 out of 10 or 2 out of 10.

Where teams get this wrong first

The most common failure isn't a missed bug — it's treating the AI feature like every other feature on the sprint board and applying the same shallow smoke test. AI features need their own test strategy document, their own regression cadence tied to model/prompt changes rather than just code changes, and — ideally — a QA owner who's allowed to say "we haven't evaluated this enough yet" without it being read as obstruction.

That's the actual differentiator on a resume or in an interview right now: not knowing what an LLM is, but having a concrete answer for how you'd test one.
